# Dawn: Day Thermal to Color for Drone Imagery

Project draft · Oct 4, 2026 · @Arsenic

## Summary

Dawn turns a daytime thermal frame from a drone into the matching daytime color image in 2 network steps, with brightness and color uncertainty maps.

It treats thermal as a one-channel image and splits the job in two. Brightness is a per-region curve of thermal intensity, if a fit check shows that works; color is generated by flow matching conditioned on a LoRA-tuned DINOv3 that learns to see thermal the way it sees daylight.

Training uses real thermal/RGB day pairs from DroneVehicle ([McCheng/DroneVehicle](https://huggingface.co/datasets/McCheng/DroneVehicle) on Hugging Face), kept only if they pass a strict alignment filter. The goal is a working, documented repo in 4 weeks on one RTX 5060 Ti (16 GB), not a paper.

## Problem and scope

The input is a daytime thermal frame from a drone (640×512, one channel); the output is the paired daytime RGB image. Invented detail is accepted; the scene's layout comes from the thermal image.

|  | In scope | Out of scope |
| --- | --- | --- |
| Data | DroneVehicle day pairs that pass the alignment filter | Night pairs, other thermal cameras |
| Input | Thermal as delivered: an 8-bit, one-channel image | Calibrated temperatures |
| Output | Day RGB: layout from thermal, brightness and color learned from pairs | Recovering detail thermal cannot see, such as text or lane paint |
| Speed | 2 network evaluations per 640×512 frame | Video, multi-frame fusion |
| Deliverable | Working repo, checkpoints, README, released alignment lists | Paper submission |

Thermal measures heat, not light, so anything without a heat signature (lane paint, signs, a car's paint color) is a learned guess.

## Design principles

1. **Layout from thermal, appearance learned.** Brightness is a per-region, per-intensity curve of the thermal image where a fit check allows it. Color, and any brightness the curve can't explain, is generated.
2. **Flow matching where the answer is ambiguous.** Colorization has many right answers; plain regression averages them into dull brown. Flow matching picks one plausible answer.
3. **DINO learns to see thermal as daylight.** A LoRA-tuned DINOv3 is trained to match its own features on the paired RGB image, and its attention map tells the generator which regions belong together.
4. **Expensive work runs once.** DINO runs once per frame; only the small velocity net repeats, for 2 steps.
5. **Real pairs, strict filters.** Only pairs that pass a box-matched alignment check train the model; residual misalignment is masked out, never learned.
6. **Uncertainty from samples.** Brightness and color maps both come from the spread of several samples.
7. **One convention everywhere.** Float32 in \[0, 1\], area averaging for every downsample, thermal warped onto the RGB frame and never the reverse, seeds derived from image IDs.

## Data

Training uses DroneVehicle day pairs that survive a strict alignment filter; the thermal image is warped onto the RGB frame, and the RGB target is never touched.

### Source

- **[McCheng/DroneVehicle](https://huggingface.co/datasets/McCheng/DroneVehicle)** on Hugging Face: about 14 GB, train, validation and test splits.
- 28,439 RGB-thermal pairs from day to night, each 840×712 with a 100-px white border, and oriented boxes for five vehicle classes labelled separately in RGB and thermal ([original paper](https://arxiv.org/abs/2003.02437)).
- The Hugging Face viewer fails on this repo, so read the files directly and confirm the folder layout (RGB vs thermal images and labels) on download.
- A recent RGB-to-thermal study cropped the border and kept 23,529 pairs after alignment ([paper](https://arxiv.org/pdf/2609.02556)). This filter is stricter and day-only, so expect fewer.

### Alignment filter

1. **Crop** the 100-px border from both images → 640×512.
2. **Day filter:** RGB median-brightness histogram plus a contact sheet; exclude dusk and anything borderline.
3. **Match boxes:** each thermal box to the nearest RGB box of the same class, mutual nearest neighbours only.
4. **Fit** a similarity transform (shift, rotation, scale) to the matched centres with RANSAC; a homography only if similarity residuals stay high.
5. **Accept** only with at least 6 matches, inlier ratio ≥ 0.6, median residual ≤ 2 px, scale within ±5%, rotation under 2° and shift under 30 px.
6. **Independent check:** gradient-magnitude correlation between thermal and RGB must improve after warping.
7. **Few vehicles:** drop at first; add an edge-correlation fallback with a stricter threshold only if the pool is small.
8. **Warp thermal onto the RGB frame.**
9. **Validity mask:** pixels pulled from outside the frame are excluded from every loss.
10. **Moving-vehicle mask:** a box whose own residual is large (it moved between exposures) is excluded from pixel losses.
11. **Audit:** contact sheets of 100 accepted and 100 rejected pairs with thermal edges drawn over the RGB.
12. **Report** counts at every stage and check for near-duplicate frames across splits. All thresholds live in `data.yaml`.

Aligned pairs and their masks are written once as PNG, so training never warps on the fly. Training augmentation: flips and 90° rotations applied to both images, plus random contrast curves on thermal, since the thermal camera rescales its gain frame by frame.

## Architecture

One DINOv3 pass on the thermal frame conditions a small velocity transformer that, in 2 steps, generates a brightness grid and a 160×128 color map; both are applied at full resolution guided by the thermal image. The output is assembled in CIELAB: L\* from the brightness path, a\*b\* from the color path.

&#91;embedded content: Dawn architecture · DINO once, 2 flow steps, brightness and color paths\]

DINO, the velocity transformer and the grid all work on the same 40×32 patches of the 640×512 frame; both uncertainty maps come from the spread of K samples.

### Encoder (runs once per frame)

- **Model:** DINOv3 ViT-S+ through timm, `vit_small_plus_patch16_dinov3.lvd1689m` (28.7M params). The weights are gated: accept the DINOv3 license on the model page and log in.
- **Input:** the aligned thermal frame at 640×512, copied to 3 channels, with ImageNet mean and std.
- **Tokens:** 40×32 = 1,280 patch tokens of 384 dims, after 5 prefix tokens (CLS and 4 registers).
- **Attention:** last block only, with fused attention turned off there and the softmax captured by a hook; patch-to-patch, heads averaged, rows renormalized, detached, as log(A + 1e-6).
- **Thumbnail:** thermal area-averaged to 40×32, one value per patch.
- **LoRA (peft):** rank 8, alpha 16, targets matched by the regex `.*blocks\.\d+\.attn\.(qkv|proj)`; a bare "proj" would also hit the patch embedding. About 0.5M trainable params.
- **Precision:** bf16 autocast, never casting the model, so timm's float32 RoPE periods stay intact.
- **Training-only head:** a color head on each patch for L\_color.

### Velocity transformer (runs 2×)

- **Tokens:** 1,280, one per DINO patch, each with 48 standardized values: 16 for its grid cell's brightness curve (8 bins × gain and offset) and 32 for its 4×4 block of the 160×128 a\*b\* map.
- **Embedding:** Linear(48→256) + Linear(384→256) of the DINO token + Linear(1→256) of the thumbnail + learned position.
- **Blocks:** 6 DiT blocks, hidden 256, 4 heads, MLP ratio 4; time enters by adaLN-Zero.
- **Attention:** scores = QKᵀ/√d + gate × DINO attention bias, one learnable gate per block initialized at 0.
- **Output:** Linear(256→48), zero-initialized. About 7M params, about 10 GMACs per step (estimate).

### Brightness path

- **Grid:** 40×32 cells × 8 thermal-intensity bins × 2 coefficients (gain, offset).
- **Guidance:** thermal intensity, 5×5 box blur, scaled to \[0, 1\]. No log: thermal isn't photon-starved like a dark photo.
- **Apply:** trilinear slice per pixel, L = gain × thermal + offset, then converted to L\*.
- **Decision rule:** `check_oracle.py` fits the best possible grid from thermal to day brightness. At about 24 dB or more, keep this path. Below that, each token also carries a generated brightness correction at 160×128.

### Color path

- The generated 160×128 a\*b\* map is upsampled with **bilateral guided upsampling** (Chen et al., SIGGRAPH Asia 2016), guided by the output L\*, so color edges follow brightness edges.
- L\*a\*b\* is converted to linear RGB, clipped to gamut, then sRGB.

### Local refiner (optional)

- Thermal is softer than RGB. A small refiner on L (inputs: L and thermal; two depthwise-separable 5×5 blocks, width 24, 9×9 field, output L + 0.1 × tanh(residual)) can sharpen edges.
- Invented detail is accepted, so the bound can be relaxed. It is the first thing to cut if time runs short.

### Uncertainty

- **Brightness and color maps:** the spread of L\* and a\*b\* across K = 4–8 samples drawn in one batch. DINO still runs once.

## Training

Stage 1 trains the flow model and DINO's LoRA together on four losses; Stage 2 (optional) trains the local refiner. Weights below are starting points.

### Stage 1 losses

| Loss | What it teaches | Computed from | Weight |
| --- | --- | --- | --- |
| L\_flow | The velocity field | MSE(v, z₁ − z₀) on standardized tokens; brightness part weighted by pixel count per cell and bin | 1.0 |
| L\_render | Images, not just coefficients | One-step estimate ẑ₁ = z\_t + (1 − t)v, un-standardized, rendered at 320×256 and compared to the RGB in L\*a\*b\* (L1) | 0.1 |
| L\_align | DINO sees thermal as it sees daylight | 1 − cosine per patch: LoRA on, thermal vs LoRA off (peft `disable_adapter()`), paired RGB | 0.5 |
| L\_color | DINO knows which colors belong where | Cross-entropy per patch against the RGB patch's histogram over 313 quantized a\*b\* bins (soft targets), after Zhang, Isola & Efros, ECCV 2016 | 0.2 |

Targets come from each batch on the GPU. The brightness grid is a weighted least-squares fit from thermal to RGB brightness, with ridge pulling sparse bins toward their cell's fit and cells toward the image fit. The color target is the RGB image's a\*b\* area-averaged to 160×128. The validity and moving-vehicle masks zero out fit weights and pixel losses.

### Schedule

- **Steps 0–5K:** DINO tokens are detached before the velocity net, so LoRA learns only from L\_align and L\_color while the velocity net trains on stable features.
- **After 5K:** all losses train everything jointly. The attention bias stays detached throughout.
- **Each image is used at 4 timesteps:** DINO runs once and its outputs are repeated.

### Settings

| Setting | Value |
| --- | --- |
| Batch | 16 images × 4 timesteps at 640×512 with gradient checkpointing on DINO; 8 × 4 if 16 GB is tight |
| Optimizer | AdamW; LoRA lr 1e-4, rest 2e-4; weight decay 0.01 (none on norms, biases, gates) |
| Schedule | 1K-step warmup, then cosine; gradient clip 1.0 |
| Precision | bf16 autocast only |
| EMA | 0.999 on velocity net, LoRA and color head |
| Augmentation | Flips and 90° rotations on both images; random contrast curves on thermal |
| Length | 30–50K steps; stop when validation plateaus |
| Logging | Every loss, each block's attention gate, validation L\* PSNR, color difference and colorfulness at 2 steps (Euler and midpoint) |

### Stage 2: local refiner (optional)

Random 256×256 crops. Input: the fitted brightness grid applied to thermal, plus the thermal itself. Loss: L1 to RGB brightness + 0.01 × |residual|, masked.

## Inference and cost

A 640×512 thermal frame costs roughly 65 GMACs at 2 steps, dominated by the single DINO pass; all figures are estimates until `benchmark_latency.py` measures them on the 5060 Ti.

1. Load the thermal frame and compute guidance.
2. Run DINO once: patch tokens, attention bias, thumbnail.
3. Draw noise and take 2 Euler steps (midpoint as an option; at 2 evaluations midpoint is one step). Optionally draw K samples in one batch for the uncertainty maps.
4. Slice the brightness grid, apply gain and offset, convert to L\*.
5. Upsample the a\*b\* map with bilateral guided upsampling.
6. Run the optional refiner.
7. Assemble L\*a\*b\*, convert to sRGB.

| Component | Cost per frame (estimate) | Runs |
| --- | --- | --- |
| DINOv3 ViT-S+ at 640×512 (1,280 tokens) | About 45 GMACs | Once |
| Velocity transformer, 1,280 tokens | About 10 GMACs | 2× (or 2K× with K samples) |
| Refiner, grid slice, color upsampling | About 1–2 GMACs | Once |

Running DINO at 320×256 (20×16 tokens, grid to match) cuts its cost about 5×, at the price of coarser color on small vehicles; useful for debugging.

## Evaluation

Every metric is measured against the real paired RGB on `test_pairs`, on whole frames and on vehicle crops from the RGB boxes, with masked pixels excluded; no baselines are needed for a project repo.

| Question | Measure |
| --- | --- |
| Is the structure right? | PSNR and SSIM on L\* against the RGB |
| Are the colors close? | Mean CIEDE2000 color difference |
| Are the colors vivid, not brown? | Colorfulness (Hasler and Süsstrunk) |
| Does it look like a photo? | LPIPS |
| Is the uncertainty honest? | Rank correlation of each sample-spread map with its actual error |
| Do vehicles survive? | All of the above on vehicle crops |
| Is it fast? | Latency per component on the 5060 Ti |

Color difference punishes a plausible color that differs from the truth (a blue car painted red scores badly), so it is read next to colorfulness and side-by-side grids, never alone.

## Risks and mitigations

The largest risk is that too few day pairs pass the alignment filter; the counts and audit sheets in week 1 settle it before any training.

| Risk | Effect | Mitigation |
| --- | --- | --- |
| Too few day pairs pass alignment | Small training set | Loosen thresholds after the audit; edge-correlation fallback for pairs with few vehicles; flips and rotations |
| Day brightness isn't a regional curve of thermal | Weak brightness path | The oracle decides; add a generated brightness correction per token |
| DINO features on thermal are weak | Poor semantics, poor color | LoRA + L\_align on real pairs; watch L\_align fall; raise LoRA rank to 16 if it stalls |
| Residual misalignment | Blurry output | Validity and moving-vehicle masks; L\_align works on 16-px patches; strict thresholds |
| Thermal gain changes frame to frame | The same scene looks different | Random thermal contrast curves in training; the grid is fitted per image |
| 16 GB is not enough at 1,280 tokens | Out of memory | Gradient checkpointing on DINO; batch 8 × 4; debug at 320×256 |
| Invented detail is read as real | Misleading output | Say so in the README; ship the uncertainty maps |

**If time runs short, cut in this order:** the local refiner; the uncertainty samples at inference; the brightness correction (if the oracle allows). Keep LoRA, L\_align, L\_color and the attention bias.

## Decision log and open items

On 6 October 2026 the project moved from synthetic dark monochrome (VisDrone) to real day thermal/RGB pairs (DroneVehicle); choices that still hold are kept below.

| Decision | Choice | Why |
| --- | --- | --- |
| Task | Day thermal to paired day RGB | Real pairs remove the camera simulator; thermal is what drones actually carry |
| Dataset | DroneVehicle via McCheng/DroneVehicle, day pairs only | Paired, with vehicle boxes in both modalities |
| Alignment | Box-matched similarity fit + edge check, strict thresholds, masks | Misaligned pairs teach blur; boxes give correspondences without cross-modal feature matching |
| Structure vs color | Brightness grid from thermal if the oracle reaches about 24 dB; color generated | Keeps the thermal layout; a measurement decides, not a guess |
| Encoder | DINOv3 ViT-S+ via timm, LoRA rank 8 (not QLoRA) | Direct access to blocks for the attention hook; the model is too small for 4-bit to help |
| DINO resolution | Native 640×512, 40×32 tokens | One token per grid cell |
| Generator | Rectified flow, 2 Euler steps | Colorization is genuinely ambiguous; MeanFlow dropped as unnecessary risk |
| LoRA objectives | L\_align on real pairs + L\_color, no segmentation loss | Pairs supply both targets; no masks exist |
| Earlier VisDrone work | Labels kept for a separate release; not used for training | Real night VisDrone frames don't fit the thermal task |
